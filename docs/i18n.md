# i18n — how locales work and how to localize a tool

Locales: `zh-TW` (default, root URLs, unchanged), `en` (`/en/…`), `ja` (`/ja/…`).
Reference migrations: `src/tools/word-counter/`, `src/tools/bmi-calculator/`, `src/tools/password-generator/`.
Copy them. If something here and those folders disagree, the folders win; then fix this file.

## 1. Architecture in one screen

```
src/i18n/
  locales.ts     LOCALES, Locale, LOCALE_INFO (htmlLang / hreflang / ogLocale / Intl tag / label / currency),
                 localePath('en', '/about/') → '/en/about/', localeHome, splitLocale(pathname)
  ui.ts          site chrome strings per locale (header, footer, search, tool page frame, home, category, 404)
  format.ts      t('{n} min', { n }), plural(), formatDate(), formatList(), compareText();
                 re-exports formatNumber / formatInteger / formatFixed / formatBytes / parseNumber from lib/format.ts
  tool.ts        ToolProps, defineToolI18n<T>(), pickStrings(), i18nAttrs()      ← server side (Tool.astro frontmatter)
  client.ts      readI18n<T>(root) → { locale, s }                              ← browser side (Tool.astro <script>)
  alternates.ts  hreflangLinks(), switcherLinks(), allLocales(), someLocales()  ← pure, tested
src/config/site.ts        brands[locale]  ← the ONE place for brand name / tagline / wordmark text
src/config/categories.ts  category text per locale (name, blurb, description, optional title)
src/tools/registry-core.ts  pure registry (tested); registry.ts feeds it the meta globs
src/views/                HomeView, ToolView, CategoryView, NotFoundView, AppView (+ app-content.ts)
src/pages/                thin routes: zh at root, src/pages/en/*, src/pages/ja/* call the same views
```

**A tool exists in a locale iff its folder has that locale's meta file**:

| File | Locale | URL |
| --- | --- | --- |
| `meta.ts` | zh-TW | `/<slug>/` |
| `meta.en.ts` | en | `/en/<slug>/` |
| `meta.ja.ts` | ja | `/ja/<slug>/` |

Any subset is allowed: zh-only (Taiwan labor law, 統一發票, 民國年…), all three, or en-only / ja-only (no `meta.ts`).
Every file of a tool must use the folder name as `slug` and the **same `category`** (the registry throws otherwise).
Pages, home grids, category pages (a category appears in a locale only when it has tools there), search,
`/<locale>/tools.json`, sitemap, hreflang and the language switcher all follow from the registry automatically.

## 2. Per-tool migration checklist (existing zh tool → add en / ja)

Do all steps; the build and `npm test` enforce several of them.

1. **`i18n.ts`** — typed dictionary, one entry per locale the tool supports:

   ```ts
   import { defineToolI18n } from '../../i18n/tool';

   export interface Strings {
     inputLabel: string;          // markup strings, used in Tool.astro frontmatter/markup
     copy: string;
     client: {                    // ONLY what the <script> needs at runtime (errors, labels set dynamically, templates)
       error: string;
       result: string;            // templates use {placeholders}: '約 {n} 分鐘'
     };
   }

   export default defineToolI18n<Strings>({
     'zh-TW': { inputLabel: '…', copy: '複製', client: { error: '…', result: '約 {n} 分鐘' } },
     en: { … },
     ja: { … },
   });
   ```

   - Move **every** user-visible string out of `Tool.astro` (labels, placeholders, aria-labels, button text, hints,
     `title=` attributes, error messages, strings built in the script). zh strings must stay byte-identical so the
     zh page does not change.
   - Text with inline markup is split around it: `lengthBefore: '長度：'`, `lengthAfter: ' 個字元'` →
     `{s.lengthBefore}<output>16</output>{s.lengthAfter}`.
   - Locale-specific presentation config may live here too (e.g. which stats to show, which BMI standard,
     whether to offer US units) — never logic.
   - Optional sub-objects (`units?: {…}`) for UI that only one locale has. Do not fill unused fields with `''`.

2. **`Tool.astro` frontmatter + root element**:

   ```astro
   ---
   import { i18nAttrs, pickStrings, type ToolProps } from '../../i18n/tool';
   import i18n from './i18n';

   type Props = ToolProps;
   const { locale = 'zh-TW' } = Astro.props;
   const s = pickStrings(i18n, locale);
   ---

   <div class="tool" data-tool="my-tool" {...i18nAttrs(locale, s.client)}>
     <label for="x">{s.inputLabel}</label>
   ```

   `i18nAttrs` writes `data-locale` and `data-i18n` (JSON of `s.client`). Keep ids / classes / `data-tool` unchanged.

3. **`<script>`** — read strings back; never import `i18n.ts` values into the script (types only):

   ```ts
   import { readI18n } from '../../i18n/client';
   import { t } from '../../i18n/format';
   import type { Strings } from './i18n';

   const root = $('[data-tool="my-tool"]');
   const { locale, s } = readI18n<Strings['client']>(root);
   out.textContent = t(s.result, { n: formatNumber(value, 1, locale) });
   ```

   Why: Astro bundles a component's `<script>` once and dedupes it across pages. Strings travel in the HTML,
   so one script serves all locales. Do **not** use `define:vars` (it inlines and duplicates the script per page)
   and do not branch on `location.pathname`.

4. **Formatting** — always pass the locale:
   `formatNumber(v, digits, locale)`, `formatInteger(v, locale)`, `formatFixed(v, 1, locale)`,
   `formatBytes(b, locale)`, `formatDate(d, locale)`; English plurals with `plural(locale, n, { one, other })`.
   Never hard-code `'zh-TW'` / `toLocaleString()` without a locale. `parseNumber` already accepts full-width digits.
   `flashButton()` / `data-copy` buttons use the page's localized "Copied" label automatically.

5. **`logic.ts`** — keep it pure. If the rules differ by market (thresholds, tax rules, reading speed, units),
   add a parameter with the zh default (`classifyBmi(bmi, standard = 'tw')`) so existing zh tests and callers keep
   working. Hard-coded zh strings in logic (e.g. labels) stay for zh compatibility, but localized UI reads labels
   from `i18n.ts`. Add tests for every new branch in `logic.test.ts`.

6. **`meta.en.ts` / `meta.ja.ts`** — `defineTool({...})`, same `slug`, `category`, `icon`, `priority`; own
   `updated`. Write native copy for that market (see §4), not a translation of `meta.ts`.

7. **Verify**: `npm test`, `npx astro check` (0 errors), `npm run build`; open `/en/<slug>/` and `/ja/<slug>/`,
   type into the tool, check the console and a 360px viewport.

## 3. Locale-only tools (phase 2 new tools)

- **en-only / ja-only**: create the folder with `meta.en.ts` (or `meta.ja.ts`) and **no** `meta.ts`. A single-locale
  tool may skip `i18n.ts` and write its strings directly in `Tool.astro`, but still accept `locale` and pass it to
  number/date formatters. If it later gains a second locale, it needs `i18n.ts` (a test enforces this).
- **zh-only**: do nothing. Unmigrated tools simply don't exist under `/en/` or `/ja/`; their Tool.astro ignores the
  `locale` prop (only ever rendered with zh-TW).
- Slugs are global across locales: a ja-only `wareki` and a zh `wareki` would be the same tool. Pick a slug that is
  free in **all** locales and not reserved (`about contact privacy terms category convert app 404 tools.json sw.js
  manifest.webmanifest en ja`).
- `related` slugs that don't exist in the tool's locale are skipped silently, so you may list future tools.

## 4. SEO expectations for meta.en.ts / meta.ja.ts

Research what people in that market actually search; use that phrase as `name` and at the start of `seoTitle`.

| Field | en | ja |
| --- | --- | --- |
| `name` (H1, cards) | the head term: "BMI Calculator", "Word Counter" | 「BMI 計算ツール」「文字数カウント」「パスワード生成ツール」 |
| `seoTitle` (brand suffix added automatically) | ~50–65 chars, head term first: "BMI Calculator: Check Your Body Mass Index in lb/ft or kg/cm" | ~28–40 字, head term first, details in （）: 「BMI 計算：身長と体重から肥満度と標準体重を計算（日本肥満学会の基準）」 |
| `description` | **~140–160 characters**, plain sentences, include 1–2 secondary terms | **~80–120 字**, です・ます調, include 1–2 secondary terms |
| `keywords` | 6–8 real queries, lowercase ("bmi calculator lbs and feet") | 6–8 real queries incl. spaced variants (「BMI 計算」「BMI 計算 ツール」) |
| `intro` | 1–2 sentences | 1–2 sentences |
| `howTo` | 3–4 steps that match the localized UI labels exactly | same |
| `sections` | 2–4 sections of genuinely useful, locally relevant content (US units, CDC/NIST/NHS, Common App limits…) | 2–4 sections, local standards and habits (日本肥満学会, 原稿用紙, 総務省/IPA, メタボ健診…) |
| `faq` | 4–6 questions people actually ask in that market | 4–6, natural Japanese questions |

Rules: no machine-translation tone; local units, standards, institutions and examples; numbers in examples must be
correct (compute them); don't mention Taiwan-specific rules in en/ja copy unless the tool is about Taiwan.
Japanese: full-width punctuation, a half-width space between Japanese and Latin/digits is fine and consistent with
existing copy; avoid 「〜」 overuse. English: sentence case in headings, US spelling.

## 5. What the framework already does (don't redo it)

- `<html lang>` (zh-Hant-TW / en / ja), `og:locale` + `og:locale:alternate`, localized brand in `<title>`.
- `<link rel="alternate" hreflang>` for every locale where the page exists + `x-default` (zh-TW if present, else en,
  else the page itself); canonical per locale. Sitemap emits the same as `xhtml:link` (astro.config.mjs).
- JSON-LD: `WebApplication` with `inLanguage` and locale currency, localized `BreadcrumbList`, `FAQPage`;
  locale homes get `WebSite` + `SearchAction` (`/en/?q=`).
- Language switcher (header, `<details>`, no JS needed): same page in other locales, else that locale's home.
- Ad slots are identical in every locale; only the "Advertisement" label is translated.
- Japanese font stack via `:root:lang(ja)` in global.css.
- `/en/tools.json`, `/ja/tools.json` (same shape + `locale`), `/en/manifest.webmanifest`, `/ja/manifest.webmanifest`,
  `/en/404/`, `/ja/404/` (nginx maps misses under `/en/`, `/ja/`).

## 6. Site-level copy you may need to touch

- Category text: `src/config/categories.ts` (`en` / `ja` blurbs, descriptions and titles mention typical tools;
  when a category's real tool list in a locale differs a lot, update its blurb/description/title).
- Chrome strings: `src/i18n/ui.ts`. Brand: `brands` in `src/config/site.ts`.
- Static pages: `src/pages/{en,ja}/{about,contact,privacy,terms}.astro`, app guide in `src/views/app-content.ts`.
- `/convert/<pair>/` landing pages are **zh-only** for now (their copy and unit names come from zh data in
  `src/conversions/pairs.ts` and `unit-converter/logic.ts`). Localizing them needs per-locale `keyword`, `aliases`,
  `note` and unit names, plus en/ja routes; treat it as its own task.

## 7. Do not

- Do not change zh-TW output of a tool while localizing it (strings byte-identical; ids/classes unchanged). Compare
  `/<slug>/` before and after.
- Do not change or remove any existing URL, slug, or `meta.ts` title/description as part of localization.
- Do not use `define:vars` in tool scripts, `is:inline` copies of tool logic, or per-locale script files.
- Do not read the locale from `location.pathname` in tool scripts; use `readI18n(root)`.
- Do not hard-code `'zh-TW'` in formatters or `toLocaleString()` without a locale.
- Do not add a locale meta file before the Tool.astro actually renders that locale (the page would show zh UI).
- Do not give a localized meta a different `category` or `slug`; keep `icon` identical (tested).
- Do not use emoji or flags (language labels are plain text: 中文 / English / 日本語); keep the light-only design.
- Do not edit `src/i18n/*`, `src/views/*`, layouts or the registry in parallel phase-2 work unless coordinated;
  per-tool folders are the unit of parallel work. If a chrome string is missing, add it to `ui.ts` in all locales.
